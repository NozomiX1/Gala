# Gala 2.0 方案

状态：草案，2026-10-12 定稿讨论，尚未开工。每完成一项就在这里更新，做完后本文件应当可以删掉。

## 目标

**让这个项目离了维护者也能转。**

1.x 的问题不在代码，而在流程：每个版本手工打包，每个兼容性修复都要维护者亲自拿到游戏、复现、写 Swift、发版。2.0 不追求兼容更多游戏，而是把这条路打通给别人走。

做完的标准：

- 推一个 tag 就能发版，用户在应用里就能更新。
- 用户遇到问题，能一键拿到足够定位问题的信息，发给维护者或任何 AI 助手。
- 不会写 Swift 的人能写出一个运行环境配置，在本机试通，再提交回来。
- 界面换成玻璃风格，新增的功能平时不出现在主界面上。

**2.0 期间维护者不亲自适配任何新游戏。**

## 不做

| 不做 | 原因 |
| --- | --- |
| 签名与公证 | 需要 Apple Developer 账号，暂不购买。用户首次打开仍需手动放行。 |
| 检测规则数据化 | 改动大。先用手动选择运行环境，有人贡献之后再看规则该长什么样。 |
| 从网络下发 profile | profile 能往 Wine 里写任意注册表，而 Wine 能访问用户的全部文件。只随应用发布。 |
| profile 的图形化编辑器、环境级组件自由搭配 | 每试一次要重建 bottle，组合一多 bottle 泛滥。 |
| 多语言、云存档、成就等启动器功能 | 与目标无关。 |

下面"推后到 2.1"一节列了想做但这次不做的东西。本文件没有列出的需求，一律进 2.1。

## 已定的决策

| 决策 | 说明 |
| --- | --- |
| 自动更新用 Sparkle | 项目的第一个第三方依赖。替换正在运行的应用并校验更新包是安全敏感的活，不自己写。 |
| profile 用 JSON | Swift 自带解析，不加依赖。每个 profile 一个文件，支持 `base` 继承。 |
| 两个 profile 目录 | 随应用发布的只读目录，加上 `~/Library/Application Support/Gala/Profiles/`。同名时用户的覆盖内置的。 |
| 手动选择运行环境 | 详情页里选。这是贡献流程的起点。 |
| 尽量多给用户能试的余地 | 开关的数量不预设，由实测决定；另外提供自由填写的高级项。细则见第 4 项。 |
| 支持 macOS 14 | macOS 26 及以上用系统玻璃，更早的系统退回普通半透明材质，判断收在一处。 |
| 界面方向 | 见第 5 项。 |

## 工作项

按顺序做。大小是粗略判断，不是工期。

### 0. 前置（小）

状态：已完成，2026-10-12。

- 合并 `chore/repo-cleanup` 分支。
- 本机运行一次 `xcodebuild -runFirstLaunch`，恢复完整构建。

### 1. 自动构建与发布（小）

状态：已写完，2026-10-12。`scripts/release.sh` 在本机跑通并检查过产物；GitHub 上的工作流要到第一次推 tag 才会真正运行，那时才算验证完。

- 一个发布脚本：`xcodegen generate` → Release 构建 → 打包 DMG。
- GitHub Actions：推送 `v*` tag 时运行脚本，把 DMG 挂到对应的 release 上。
- 版本号只在 `project.yml` 里改。

完成标准：推一个 tag，几分钟后 release 页面上出现可用的 DMG，全程不碰本机。

注意：tag 保持 `vX.Y.Z` 格式，产物保持 `.dmg` 后缀。1.x 的更新检查靠这两点找到新版本，2.0 要靠它把老用户带过来。

### 2. Sparkle 自动更新（中）

状态：代码和发布流程已完成，2026-10-12；真实更新测试未做。

- 已做：接入 Sparkle 2.10.0、生成密钥（公钥在 `project.yml`，私钥在钥匙串的 `gala` 账户下）、菜单和"运行环境"里的检查更新、发布脚本生成带签名的更新清单、删除旧的更新检查。更新清单的地址是 `releases/latest/download/appcast.xml`，不需要另外搭页面。
- 发布 2.0 时要做：把私钥放进仓库的 `SPARKLE_PRIVATE_KEY`；按下面的完成标准做一次真实更新测试。
- 挪到第 5 项：设置里的"自动检查更新"开关。在那之前默认开启。

- 在 `project.yml` 里加入 Sparkle 包，`Info.plist` 里声明更新源地址。
- 生成更新签名密钥：私钥放 GitHub Secrets 和本机钥匙串，公钥进 `Info.plist`。
- 构建流程里生成并发布 appcast（更新清单）。
- 应用菜单加"检查更新…"，设置里加"自动检查更新"。
- 删除 `AppUpdate.swift`、它的测试、以及"运行环境"弹窗里的更新界面。

完成标准：在一台真实机器上，从 2.0.0 通过应用内更新到 2.0.1，重启后版本正确，游戏库和 bottle 都在。

### 3. 诊断、调试启动、命令行（中）

状态：已完成，2026-10-12。没有用真实的 Wine 和游戏跑过，只用一个替身程序验证了整条流程。

- 已做：引擎识别的候选、分数和依据对外提供；每个游戏保留最近三次启动的日志；启动时可选的调试输出；诊断报告（文本和 JSON，路径里的用户名已去掉）；命令行随应用一起分发，有 `list`、`diagnose`、`configure`、`launch`、`guide`。
- 配置环境和启动前的检查原来写在界面的代码里，现在挪进了 GalaKit 的 `GameRuntime`，界面和命令行共用。
- 命令行的 `configure` 和 `launch` 可以带只对这一次生效的选项：换一种引擎的运行环境、追加 DLL 设置、追加环境变量、换区域。"待验证的假设"前两条就用它来测。
- 挪到别的项：界面上的导出和复制按钮在 5b；issue 模板在第 6 项；"求助信息"里的可调设置清单要等第 4 项有了开关的数据。
- 已定，2026-10-13：从界面启动时记录 Wine 的报错行（原来完全不记录，第一次失败时日志是空的）。ハミダシ 正常启动一次的日志是 27 行，其中 19 行是每次都有的无害内容，诊断信息里会滤掉。

- `EngineDetector` 把候选引擎、分数和依据对外提供。这些现在算完就丢弃了。
- 每次启动保留 Wine 日志到 Gala 自己的目录，只留最近几次。现在是退出即删、只留最后 500 个字符。
- "调试启动"：打开 Wine 的日志输出。现在固定是全部关闭。
- 诊断文本生成放在 GalaKit 里，是纯函数，有测试。内容：Gala、系统、芯片、Wine 版本；引擎识别结果和依据；游戏目录的文件名列表；当前运行环境和开关；日志结尾和所有报错行。路径里的用户名替换成 `~`。
- 命令行入口，随应用一起分发：列出游戏、查看某个游戏、用指定环境和开关启动、输出诊断、输出排障指南。支持 `--json`。
- 界面：详情页的"导出诊断信息"和"复制求助信息"。后者复制前先让用户看到内容，文字要自己就够用：诊断信息、可调的设置清单、要求对方用界面上的原话回答。
- issue 模板，要求附诊断文件。

完成标准：拿一个启动失败的游戏，只看导出的文本，就能知道它被识别成什么、用了哪个环境、报了什么错；用命令行能换一个环境启动它并拿到日志位置。

### 4. Profile 数据化（大）

状态：进行中，2026-10-13。

- 已做：文件格式定稿（`id`、`name`、`notes`、`base`、`version`、`wine`、`components`、`managedComponents`、`dllOverrides`、`registry`、`registryDelete`、`verifiedGames`）；8 个现有环境写成文件，先用测试证明与原来的 Swift 定义逐项相等，再把 Swift 里的定义删掉改为读文件。
- `version` 变成可选：每个 bottle 的标记里多存一个"配方指纹"，文件内容一变指纹就变，不需要人记得去加版本号。只有想在配方内容不变的情况下强制所有人重配时才需要加。1.x 写下的标记没有指纹，仍按版本号判断，所以老用户不用重配。
- 用户目录：数据目录下的 `Profiles/`。同名文件覆盖内置的；读不出来或 `base` 不存在的文件会被跳过并报告，不影响其余的。
- 按游戏选择：游戏库里每个游戏多一个可选的"手动选的运行环境"。预设、bottle 标记、用哪个 Wine、`G:` 盘映射、视频转码，现在都跟着游戏实际用的运行环境走，不再只看引擎。家族计划那几条固定的注册表项挪进了它的文件。
- 命令行：`profiles` 列出运行环境和有问题的文件，`use <游戏> <环境>` 切换并保存，`--profile` 临时换一次。用替身工具把"放文件、选中、配置、启动、诊断、改文件后自动发现过期、切回默认"整条流程走通了；还没用真实游戏走过。
- 已知的限制：改了文件再配置，只会添加和覆盖。从文件里删掉的 DLL 设置或注册表项不会从已建好的 bottle 里消失，要删掉那个 bottle 的文件夹重来。把 DLL 设置改成启动时才带上可以解决一半，留到做开关时一起处理。
- 已完成：两个有名字的开关，"视频播放方式"和"图形渲染"，都在启动时生效，不改环境；定义只写在一处（`LaunchSwitch`），面板和命令行指南都从它生成。"文字区域"等日文原版游戏测过再加。
- 已完成：运行设置面板（环境选择、开关、三个高级项、导出为文件）。
- 还没做：把预设里的 DLL 设置从"装进环境"挪到"启动时带上"。
- 已完成：失败提示上的两个按钮、求助信息的预览与复制、导出诊断信息。

动手前先验证"待验证的假设"里的前三条，结果会改变这一项的设计。

- **格式**：标识、名称、说明、`base`、版本号、Wine 变体、要装的组件、DLL 设置、注册表的写入与删除、已验证的游戏列表。少数必须写代码的行为（家族计划的 `G:` 盘映射和注册表路径、甜蜜女友3 的视频转码）留在代码里，文件里用开关名引用。
- **开关也是数据**：名称、说明、选项、每个选项对应的启动设置。界面、求助信息、命令行指南都读这一份，名字只写一处。
- **尽量多给用户能试的余地，分三层**：
  1. 界面上有名字的开关。准入条件有两个：对应一个真实出现过的症状，说明文字按症状写；实测确认"改完直接启动就生效，只影响这一个游戏"。数量由测试结果决定。
  2. 界面"高级"一栏里自由填写的三项：自定义 DLL 设置、环境变量、启动参数。这三项的存储和启动时的读取 1.x 就有，只是没有界面。AI 助手可以直接告诉用户往里填什么。
  3. profile 文件和命令行，不设限。
- **把能挪的设置从"装进环境"挪到"启动时带上"**：现在预设里的 DLL 设置是写进 bottle 注册表的。改成启动时按游戏带上之后，只差几条 DLL 设置的环境可以共用一个 bottle，切换也不用重新配置。能挪哪些，以下面的实测为准。
- **存储**：每个游戏多存"选定的运行环境"和"开关取值"。`Engine` 枚举保留，只用于检测；没有手动选择时，用引擎对应的默认环境。游戏库格式升到版本 2，迁移前备份。
- **加载**：内置目录加用户目录，带校验。用户文件写错时在界面上给出清楚的错误，不能让应用崩溃。
- **安全网**：先从现有 Swift 代码生成 8 个 JSON，用测试断言两者完全等价，然后再删 Swift 里的预设。
- **界面**：运行设置面板里的环境选择、开关、"把当前配置导出为文件"。
- **切换环境时的存档**：换环境等于换 bottle，写在 bottle 里的存档会留在旧环境。2.0 只做提示，不做迁移。

完成标准：把一个新的 JSON 放进用户目录，重启 Gala，就能在某个游戏上选中它、配置、启动，全程不碰 Swift；现有 8 个环境的行为和 1.x 一致，有测试保证；有一页贡献说明。

### 5. 界面（大）

方向已经通过样稿定下来：

- **布局**：没有侧栏。主窗口是封面墙，四个筛选项是工具栏里的分段控件。点封面进入详情页。
- **详情页**：封面放大模糊后做背景，上面一层深色，内容居中，白色文字。浅色和深色模式下都是这个样子。右边一栏和封面等高。上面是标题、中文标题、"开发商 · 发售日期"、状态；一行放大的按钮（启动、收藏、已通关、运行设置、`···`）居于状态和底部面板的正中（更改启动文件和两个移除操作留在 `···` 里）。底部贴着封面底边是一块两行三列的面板：游玩时间、上次游玩、通关时长；VNDB 评分和投票人数、中文（官方中文、民间汉化、无中文）、引擎。配置进度和失败提示出现在按钮行的正上方，和它一起居中。不放简介和截图。这些 VNDB 信息添加游戏时取一次并存进游戏库。
- **视觉语言**：玻璃。只用在能点的控件和浮起来的面板上，正文直接放在背景上。
- **封面墙背景**：跟随系统外观，取最近玩过的游戏的封面。深色是模糊封面加深色遮罩；浅色是更重的模糊、减半的饱和度、加一层厚的灰白遮罩。这些数值做成容易调的常量。
- **新功能的位置**：主界面不加新控件。环境选择和开关在"运行设置"面板里，从启动按钮那一行的图标进入；启动失败时，失败提示里直接给出"换个运行环境试试"和"复制求助信息"。
- **设置窗口**：标准的设置窗口，三页：通用、运行环境、数据。两个清除操作单独放在"数据"页。
- **添加游戏的入口**：工具栏上不放加号。封面墙最后一格是和封面一样大的虚线卡片，只在“全部”且没有搜索时出现；整个窗口都接收拖放，拖动时卡片亮起；另有菜单项和 ⌘N。
- **顺带修正**：封面下面显示原文标题而不是罗马音。

分两步做：

- **5a**（已完成，2026-10-12，在 macOS 27 上用示例游戏库截图看过；macOS 14 上的外观没有验证）：封面墙、详情页、设置窗口，只承载现有功能。可以在第 3、4 项之前或同时做。先只做详情页，看过真实的系统玻璃再铺开。
- **5b**：运行设置面板、失败提示、导出与复制按钮。依赖第 3、4 项。

完成标准：样稿里的每个画面都有对应的真实界面；在 macOS 14 上外观正常；浅色和深色都检查过。

样稿是一次性的 HTML 文件，保存在 `prototype/ui-2.0` 分支上，不进主分支。

## 待验证的假设

前三条决定界面上能有哪些开关。它们要看游戏画面才能判断，只能由手里有游戏的人来测。先做完第 3 项的命令行，测试就是"按清单逐条运行一个命令，记下片头是否正常"。

| 假设 | 怎么验证 | 不成立的话 |
| --- | --- | --- |
| 在 `common` 的 bottle 里，启动时带一条 DLL 设置就能达到 `kirikiri` 环境的效果 | **已验证成立，2026-10-13。** 在真实的 bottle 里加载 quartz 并看 Wine 用的是哪一份：启动时的设置盖过了注册表里的设置。千恋万花在 `common` 里启动、画面、声音正常。游戏内的视频播放没有走到 | — |
| 转区只需要改启动时的语言环境 | 同一个 bottle 分别用中文和日文环境启动日文原版游戏。目前 codepage 是建 bottle 时写进注册表的，而且界面上没有地方选日文，所以现有的 bottle 全是中文 codepage | "文字区域"不能做成开关，改为按区域分开的运行环境 |
| DXMT 能做成按游戏的开关 | **已验证成立，2026-10-13。** 决定用不用 DXMT 的只有"用哪一套 Wine 启动"：带 DXMT 的 Wine 对着没装过任何 DXMT 东西的 `common` bottle 启动ハミダシ，标题画面正常；普通 Wine 对着 `artemis-d3d11` 的 bottle 启动，黑屏并报 `CreateVertexShader` 错误。千恋万花（D3D9）用带 DXMT 的 Wine 启动不受影响。随后用同一组合看了 logo 和视频，播放正常。细节见 `docs/runtime-lessons.md` | — |
| Sparkle 能给未签名的应用做更新，且更新后不再被系统拦截 | 第 2 项的完成标准本身就是这个测试 | 退回到"下载 DMG 手动替换"，保留更新检查 |
| GitHub 的构建机器能构建本项目 | 已确认有 `macos-26` 机器；能否构建通过要等第一次推 tag。目前没有 macOS 27 的机器，所以只能用到 macOS 26 的接口 | 发布脚本在本机运行，只自动化上传 |
| 真实的系统玻璃效果符合预期 | 5a 先做详情页 | 调整材质用法，样稿只能确认布局 |

第三条是写这份方案时才发现的，讨论时把它当成了可以立刻切换的开关。

第三条的实测还带出两件事，已修：`artemis-d3d11` 往 bottle 里复制 DLL 的那一步不起作用，而且会把刚装好的 quartz、amstream、d3dcompiler_47 原版覆盖回 Wine 自带的，所以这个环境实际跑的和文件里写的不一样；用户文件只写 `"wine": "dxmt"` 而不写 `managedComponents` 时，没下载过 DXMT 的机器上不会去下载。现在不再复制，`"wine": "dxmt"` 自带下载；两个 Artemis D3D11 环境去掉了从未生效的 d3dcompiler_47。1.x 配置的 bottle 没有记录指纹，仍被认为是当前的，不需要重新配置；它们停留在旧状态（quartz 是 Wine 自带的），那个状态一直是能用的。

## 风险

- **没有 Wine 升级路径。** 现在只在"完全没装 Wine"时才下载，改版本号对老用户不生效，DXMT 变体还会因为找不到目录而报错。2.0 不解决，但第 4 项设计格式时给依赖版本留好位置。
- **游戏库格式变更后不能降级。** 1.x 打不开 2.0 写出的游戏库。迁移前会备份，README 里写明。
- **范围蔓延。** 讨论过程中已经加了不少东西。规则：这里没列的进 2.1。
